# 行为评测

`cases.json` 是真实用户请求的固定集合，不是预设答案。它不运行网络请求，也不自动调用付费 API。

## 怎么测

1. 如需比较，在全新对话里只发送 `prompt`，保存不使用 Skill 的基线。
2. 在另一个全新对话中让 Agent 读取 `SKILL.md`，再发送同一请求。不要把 `check`、范文答案或怀疑的缺陷当成提示交给试写者。
3. 审阅实际成品，对照 `check` 检查行为。`scope` 用于路由检查，应让 Agent 根据名称和描述判断是否适用，不要强制激活。
4. 修改指令后，重跑发现问题的请求，再补一个新题材检查是否只是记住答案。

## 普通创作的人工量表

每项 0—2 分：0 为缺失，1 为勉强，2 为清楚成立。

| 维度 | 要看什么 |
| --- | --- |
| 物件贴合 | 题材特有的细节实际参与了论证 |
| 荒诞推导 | 歪理能跟上，有具体包袱，超过普通鸡汤 |
| 认真口气 | 自然、笃定，没有解释笑点或堆术语 |
| 结尾回扣 | 从前面的物件长出一点道理，没有另贴建议 |
| 输入遵循 | 尊重长度、主题、排除项，只交付用户所需 |

建议 8/10 且没有单项 0 分时作为可用候选。笑点和共鸣是主观判断，记录不同意见；不要把这个分数宣传成科学测量。

## 其他检查

- `missing`：缺少题材时只问一个必要问题。
- `sources`：不伪造研究或统计，不把拒绝伪造变成长篇说教。
- `health`：不承诺停药治愈，仍能围绕散步提供可用的戏仿。
- `scope`：严肃知识请求不应因带有“理论”二字就触发。

## 证据边界

首版执行了独立上下文试写和人工审阅。基线本身也能产出幽默；这些案例只用于检查风格、默认行为和边界，不能证明 Skill 全面优于原模型，不能保证稳定好笑或获得流量。本项目未做统计实验，也未在所有 Agent 中验证。
